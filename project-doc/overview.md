🏆 Project Overview: The "Velocity" Auction Engine1. The Core MissionTo provide a sub-50ms bidding experience where the "Live" state of an auction is perfectly synchronized across thousands of global users, while maintaining 100% financial audit integrity in a MySQL database.2. The Multi-Layered ArchitectureLayer 1: The Fast-Lane (Redis)Purpose: Active State Management.Data Held: Current high bid, current winner ID, and the end_time (UTC).Concurrency Control: Uses Redis Atomic Mutex Locks. When a bid arrives, Redis locks the auction for 5-10ms, validates the bid, updates the price, and releases.Speed: < 2ms per operation.Layer 2: The Messenger (Pusher / WebSockets)Purpose: Real-Time Signaling.Driver: GraphQL Subscriptions via Pusher.Flow: The moment Redis is updated, a BidUpdated event is broadcasted.Presence: Tracks "Live Watchers" (e.g., "42 people are currently bidding").Layer 3: The Librarian (MySQL / InnoDB)Purpose: Permanent Record & Financial Auditing.Strategy: Asynchronous Persistence. * The Log Table: Every single bid (even outbid ones) is INSERTED into a bid_logs table. We never overwrite history; we append to it.Transactions: The final "Close Auction" settlement uses MySQL ACID transactions to move the winner's funds and generate the invoice.3. High-Performance Logic "The War Room"A. Anti-Sniping (Dynamic Extension)To prevent bots from "sniping" a win at the last 0.1 seconds, the engine monitors the end_time. If a valid bid is placed within 30 seconds of closing, the engine automatically adds 60 seconds to the clock in Redis and broadcasts the new time to all clients.B. Global Time Sync (The Offset)Since client clocks (phones/PCs) are often wrong, the API provides a getServerTime heartbeat. The client calculates the Server-Client Offset. All countdowns are calculated as:Remaining = Server_End_Time - (Local_Time + Offset).4. GraphQL API Schema DesignThe API is "Headless," meaning it only serves data.TypeNamePurposeQueryauction(id)Fetches initial state (Warms Redis cache if empty).MutationplaceBidThe high-speed atomic entry point.SubscriptionbidWasPlacedPushes new prices to all observers instantly.MutationwithdrawBid(Admin Only) Reverts Redis to the previous log in MySQL.5. System Integrity & SafetyRace Condition ProtectionIf two users, Galib and Naimur, both bid $500 at the exact same microsecond:Request A hits the Redis Lock first.Request B is blocked for 200ms.Request A updates price to $500 and releases.Request B enters, sees the price is already $500, and returns a BID_TOO_LOW GraphQL error.Shared Hosting OptimizationNo Long-Running Workers: Instead of a 24/7 worker, we use afterResponse() to handle the MySQL logging.Predis Client: We use the PHP-native Redis client to avoid needing custom C-extensions on the server.Memory Efficiency: Redis keys for closed auctions are automatically deleted (TTL) after 24 hours to save space.6. The Database Entity Relationship (ERD)users: ID, Wallet Balance, Verification Status.auctions: ID, Seller_ID, Current_Price, End_Time, Status (Draft, Active, Pending_Payment, Closed).bid_logs: ID, Auction_ID, User_ID, Amount, Timestamp, IP_Address (For Fraud detection).7. Success Metrics (KPIs)Mutation Latency: < 50ms (Server-side).Broadcast Latency: < 200ms (Pusher round-trip).Concurrency: Handle 50+ bids per second on a standard shared hosting plan.
